# lhg-fm-assumption：业务假设清单化

> 目标：把"老板拍脑袋的业务判断"变成一张可审计的假设表。核心纪律：**每个数字都有来源，猜的必须标注"估计"**。
> 适用对象：公司整体、单个项目、单店/单产品的 3~5 年财务预测建模。

## 1. 何时使用

- 用户说"帮我建个财务模型"→ 先跑本 skill，再搭三表
- 用户已经给了假设表 → 跑第 5 步（完整性检查）即可
- 模型结果离谱 → 先回查假设表（八成是假设的问题，不是公式的问题）

## 2. 必需假设清单（六项）

| 假设 key | 中文 | 含义 | 典型提问 |
|---|---|---|---|
| `revenue_growth` | 收入增速 | 每年收入增长 % | "去年收入多少？今年预计增长多少？" |
| `gross_margin` | 毛利率 | （收入−成本）/收入 | "毛利率大概多少？成本主要是哪些？" |
| `opex_rate` | 费用率 | 期间费用/收入 | "人工+租金+营销占收入几成？" |
| `tax_rate` | 所得税率 | 25% / 小微优惠税率 | "公司所得税率？是否享受优惠？" |
| `capex_rate` | 资本开支率 | 资本开支/收入 | "每年要投多少买设备/装修？" |
| `discount_rate` | 折现率 | DCF 用 | "期望回报率？没概念就先按 10%" |

**缺失处理**（审计脚本 FM-ASSUMP-001 会硬校验）：
- 用户能给 → 直接用，来源标"用户给定"
- 有公开信息（如上市公司年报）→ 用，来源标"公开信息"
- 都没有 → 按保守口径估计，来源标"估计"，并在交付时明确告诉用户"这 2 项是估计的，结论对它们敏感"

## 3. 从业务描述提取假设（翻译手册）

| 用户说的话 | 翻译成假设 | 保守处理 |
|---|---|---|
| "月营收 50 万，一年涨 30%" | revenue_growth=0.30 | >30% 亮黄灯，要依据；无依据按 0.20 |
| "毛利六成" | gross_margin=0.60 | — |
| "人工是大头，占三成" | opex_rate 至少 0.30（含租金营销再往上加） | 费用只会多不会少，往上取整 |
| "刚开业，设备投了 200 万" | capex_rate 按首年单独列，不摊到每年 | 重资产首年 capex 单列 |
| "小规模纳税人" | tax_rate 按实际优惠税率，不许直接用 25% | 问清楚，别拍脑袋 |
| "希望年化 15%" | discount_rate=0.15 | 用户没概念默认 0.10 |

**翻译纪律**：
- 用户说的"大概""左右" → 取保守端（收入取低、费用取高）。
- 同一个假设用户前后说的不一致 → 列出来问，不许自己挑一个。
- 定性描述（"生意很好"）翻译不成假设 → 打回要数字。

## 4. assumptions.csv 格式

表头：`假设,值,说明`

```csv
假设,值,说明
revenue_growth,0.15,用户给定：近三年平均增速
gross_margin,0.60,用户给定：当前毛利率
opex_rate,0.30,估计：人工25%+租金营销5%
tax_rate,0.25,公开信息：一般企业所得税率
capex_rate,0.08,用户给定：每年设备更新约80万
discount_rate,0.10,估计：用户无明确要求，按保守口径
```

值统一用小数（0.15 不是 15%），避免百分比/小数混用导致的公式错误。

## 5. 完整性检查清单

- [] 六项必需假设齐全？
- [] 每个假设有来源标注（用户给定/公开信息/估计）？
- [] 估计类假设已在交付说明里点名？
- [] 收入增速 >30% 的有依据？
- [] 小数与百分比口径统一？
- [] 假设表已落盘，后续三表搭建引用的是同一张表？

## 6. 反模式（不许这么干）

- ❌ 假设缺了两项，悄悄用"行业平均"补上还不标注
- ❌ 把"估计"写成"根据年报"，伪造来源
- ❌ 收入增速拍 50%，费用率拍 10%，模型"看起来很美"
- ❌ 百分比和小数混用（revenue_growth 一会儿 15 一会儿 0.15）
- ❌ 建模中途改假设不更新 assumptions.csv（后面审计对不上）
- ❌ 用"精确到小数点后 4 位"的假设伪装精确（假设是估计，精确是幻觉）

## 7. 常见问题

- **Q：用户说"假设你定就行"？** A：不行。假设是用户的业务判断，你只能给"保守口径建议值"并标注"估计"。定假设是用户的权责。
- **Q：初创公司没有历史数据？** A：收入用"单店模型×店数"倒推，费用按同行经验估计并标注；预测期缩到 3 年，不许做 10 年预测。
- **Q：toB 项目收入看大客户？** A：收入假设拆成"存量客户续约 + 新增客户"，别合成一个增速；大客户依赖在说明里点名（集中度风险）。
- **Q：折现率到底定多少？** A：用户有要求按用户的；没有按 10%；敏感性分析里会对它做 ±20%，结论会告诉你它有多敏感。
- **Q：假设太多，表很长？** A：必需六项是底线；业务特殊的（如高库存）可加项，但每加一项都要有来源。假设不是越多越好，是越可审计越好。
- **Q：用户给的假设明显离谱（如毛利率 95%）？** A：先复述确认："你确认毛利率 95% 吗？这意味着成本只有 5%。" 用户坚持就用，但标注"用户给定（已提示异常）"；模型交付时敏感性分析会暴露它的影响。
- **Q：toC 订阅制业务，收入增速怎么定？** A：拆成"用户数增速 × ARPU 变化"，别合成一个数。续费率单独列假设——订阅制模型的命门是续费，不是新客。
- **Q：假设表要不要版本管理？** A：要。每次改假设，assumptions.csv 另存一份带日期（如 assumptions-20261011.csv），模型说明里写"本次用 v3 版假设"。改假设不留痕，复盘时说不清。

## 8. 附：奶茶店单店模型假设表示例

| 假设 | 值 | 说明 |
|---|---|---|
| revenue_growth | 0.10 | 用户给定：成熟商圈单店年增约 10% |
| gross_margin | 0.65 | 用户给定：茶饮毛利率约 65% |
| opex_rate | 0.45 | 估计：人工 25%+租金 15%+其他 5% |
| tax_rate | 0.05 | 公开信息：小规模纳税人优惠口径（示例） |
| capex_rate | 0.03 | 用户给定：每年设备维护约 3% |
| revenue_base | 6000000 | 用户给定：年营收 600 万 |
| discount_rate | 0.10 | 估计：用户无明确要求，保守口径 |

**读法**：这张表是模型的"地基"。任何人拿到这张表，都应该能复算出三表——复算不出来，说明假设或公式有断层。

**地基自检三问**（写完假设表问自己）：
1. 如果把这张表给另一个人，他能不问我就搭出同样的三表吗？（不能 → 说明里缺东西）
2. 哪个假设我最没把握？（把它标红，它就是敏感性分析的第一个变量）
3. 有没有"看起来精确但实际是猜"的数？（有 → 来源改成"估计"，小数点后别留 4 位）

**假设评审会（给团队用的流程）**：假设表定稿前，把"估计"类的假设单独拎出来过一遍，每条问"有没有更好的依据"。过一遍通常能消灭一半的拍脑袋。

**假设与敏感性的联动**：评审会上被标红"最没把握"的假设，直接写进敏感性分析的变量清单（lhg-fm-sensitivity 第 2 步）——两张表用同一套"没把握清单"，不许各说各的。

**假设变更日志**：assumptions.csv 每次改动，在模型说明里记一行"日期/改了什么/为什么"。三个月后回看，你会感谢这行字。

**一句话总结**：假设表是模型里唯一"允许主观"的地方——主观可以，但必须诚实标注。

## 9. 自检与反馈

**质检门**：
- [] 六项齐全且来源三分类标注完整？
- [] 估计类假设在交付说明中点名？
- [] 审计脚本 FM-ASSUMP-001 通过？

**标准冒烟用例**：用插件 `fixtures/model-good/assumptions.csv` 确认通过；用 `fixtures/model-bad/assumptions.csv` 确认 FM-ASSUMP-001 被命中。

**发现问题**：到本仓库提 issue（标题前缀 `[lhg-fm-assumption]`），描述：业务类型、哪条假设定不准、期望行为。
